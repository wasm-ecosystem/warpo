# Warpo GC 栈槽着色优化：实现与实测

## 1. 结论

已经在 [Warpo](../warpo/) 实现并默认启用了 **degree-first / MCS 双候选着色，以实际发射的根帧大小择优**。

对 Warpo 自身使用的 AssemblyScript 前端源码进行编译，最终实现的测量结果如下：

| 指标 | 旧着色 | 新着色 | 结果 |
| --- | ---: | ---: | --- |
| GC lowering 阶段逐函数根帧大小之和 | 19,572 B | 17,496 B | **减少 2,076 B，10.61%** |
| 得到更小根帧的函数 | — | 301 个 | 占原来有根帧的 1,404 个函数的 21.44% |
| 生成的前端 Wasm 文件 | 544,939 B | 544,925 B | 减少 14 B，0.00257% |
| 原生编译器完整编译耗时，中位数 | 3,327.304 ms | 3,393.100 ms | **增加 1.98%** |
| 其中 `Lowering` 阶段，中位数 | 308.844 ms | 340.108 ms | **增加 10.12%** |
| 生成的前端执行编译任务，`CompilationHIR_Compilation` 中位数 | 460.216 ms | 440.584 ms | 本轮减少 4.27%，**尚不能认定为稳定加速** |
| 上述自举任务完整进程耗时，中位数 | 866.245 ms | 852.645 ms | 本轮减少 1.57%，**尚不能认定为稳定加速** |

**本节是首轮静态实验。新增的动态峰值、清零、扫描、RAM 配置以及 40 对未插桩计时，见第 10 节。10.61% 不是程序运行速度提升。**
运行计时存在明显波动：前一轮相同 Wasm 的测量中，前端执行阶段反而慢了 0.95%，完整进程慢了 1.06%。两轮的方向不一致，不能只挑最终一轮的正数作为加速结论。

这里的根帧大小之和是在 GC lowering 时记录的逐函数静态指标；函数不会同时全部执行，后续通用优化也可能内联、消除函数或改写代码。因此它不是最终程序的动态峰值 shadow-stack 占用，更不是堆内存、RSS 或车端内存节省比例。

## 3. 设计思路

### 3.1 保留原算法，额外生成 MCS 候选

原实现使用 degree-first 排序，再贪心分配颜色。它很便宜，但不同遍历顺序可能导致额外颜色。

新候选借鉴 Julia GC lowering 中的 Maximum Cardinality Search 思路：

1. 每个未选择节点维护权重，表示已经选择的邻居数量。
2. 选择权重最大的节点；并列时选择 SSA 编号较大的节点，保证结果可复现。
3. 给该节点分配邻居尚未使用的最小颜色。
4. 更新未选择邻居的权重，直到完成。

实现位于 [Liveness.cpp](../warpo/passes/GC/Liveness.cpp)，接口位于 [Liveness.hpp](../warpo/passes/GC/Liveness.hpp)。
保持现有冲突图数据结构，采用简单的二次复杂度实现，不引入依赖。
这只是另一个启发式候选，**不保证任意冲突图都达到最优着色**，也不声称是新的图着色算法。

### 3.2 必须比较实际根帧，不能只比较颜色数

Warpo 的冲突图还包含调用者负责管理的参数等分析节点。它们会占用颜色，却不一定在当前函数中发射根存储。

因此，“全图使用的颜色更少”不等于“当前函数的根帧更小”。

新实现让两个候选分别通过现有的 `Process` 映射逻辑，再计算：

```text
没有实际根存储：frameBytes = 0
否则：frameBytes = max(实际根存储的 offset) + ShadowStackElementSize
```

当前 `ShadowStackElementSize` 为 4 字节。只有 `mcsFrameBytes < legacyFrameBytes` 才采用 MCS，否则保留旧结果，包括相等的情况。

具体实现见 [StackAssigner.cpp](../warpo/passes/GC/StackAssigner.cpp)。
`StackPosition::getFrameSize()` 同时供 [PrologEpilogInserter.cpp](../warpo/passes/GC/PrologEpilogInserter.cpp) 使用，避免候选择优和真正分配使用不同的大小定义。

另外，旧结果为 0 或 4 字节时跳过 MCS：两种着色映射的是同一组实际存储，不可能在保留非空存储的同时把一槽帧变成零槽帧。
本次完整前端中有 632 个原来就是一槽帧的函数。

### 3.3 没有改变哪些语义

- 不改变存活性分析和冲突边。
- 不改变 GC marker 的插入位置或提前存储策略。
- 不改变 shrink-wrap 的根保护区域。
- 不改变 GC runtime、根槽宽度和后端 ABI。
- 不要求 WasmGC，不需要升级车上的 Wasm-to-machine-code 编译器。
- 不顺带实现 safepoint-only 冲突图、延迟写根或死槽清零。

也就是说，本次只改善“合法冲突图如何分配到已有根槽”，不把前文设计中的其他优化混入实验。

## 4. 为什么双候选比直接替换更稳妥

测试中使用了下面这个简单路径图：

```text
1 -- 5 -- 3 -- 2 -- 4 -- 0
```

在当前确定性排序下：

- 旧 degree-first 使用 3 色，MCS 使用 2 色。
- 所有节点都有实际存储时，根帧从 12 B 降到 8 B。
- 如果只有节点 4 有实际存储，旧着色对应 4 B，而 MCS 对应 8 B；不能因其全图颜色更少就采用它。
- 只让节点 0、4 产生存储时，两种根帧都是 8 B，但偏移布局不同；新实现保留旧布局。

这些是受控单元测试，不是实际程序性能数据。它们覆盖“更少颜色仍可能更差”和“平局不改布局”两个容易遗漏的条件。

所有计时均关闭 `GCColoring` 调试输出。每组预热 2 次、正式测量 9 次，每轮交替旧、新顺序。下表单位均为 ms，范围为 9 个正式样本的最小值～最大值。

## 9. 如何评价这次优化

本次已证明：

- 在真实的大型前端输入中，现有启发式确实存在可改善的根槽分配。
- 不改变根存储位置和后端 ABI，也能减少静态根帧分配指标。
- 用实际发射帧大小择优，能够避免“全图颜色更少却使实际帧变大”的错误选择。
- 代价是多跑候选分配，当前测得完整编译耗时增加约 1.98%。

上述静态实验本身尚不能证明：

- 量产车端的执行加速。
- 动态 shadow-stack 峰值、峰值 RSS 或堆占用下降。
- GC 扫描字节数、暂停时间的下降幅度。
- 任意程序都减少根帧，或者 MCS 是最优着色。

因此，准确的对外表述是：**在前端自编译输入上，GC lowering 的逐函数根帧大小总和降低 10.61%，以约 1.98% 的完整编译时间增量换取；当前没有可确认的稳定运行加速。**
设计的仓库内说明见 [GC shadow-stack slot coloring](../warpo/docs/tech/lower/gc/coloring.md)。

## 10. 四项潜在价值的动态量化

本节补充前文没有测量的项目，采用**最终优化后的 Wasm 动态计数**，不再使用逐函数静态帧大小之和代替实际收益。

| 问题 | 实测结论 |
| --- | --- |
| 能否降低动态根栈峰值？ | **能**：真实前端自编译减少 8.91%；128 层类型嵌套减少 29.75% |
| 能否减少清零、根扫描？ | **能**：自编译的帧清零量减少 10.02%，根扫描字节数减少 8.38% |
| 能否提高运行速度？ | **未证明**：40 对计时的经验置信区间包含零 |
| 能否降低实际 RAM 配置？ | **根栈预算可以降低；完整线性内存未观察到下降** |

### 10.1 方法：计数最终代码，计时不插桩

新增可复现工具：

- [gc_profile.mjs](../warpo/tests/bootstrap/gc_profile.mjs)：最终 Wasm 的插桩及精确校准。
- [gc_dynamic_bench.mjs](../warpo/tests/bootstrap/gc_dynamic_bench.mjs)：负载生成、编译、动态计数、内存配置对照和计时。
- [CompilerImpl.cpp](../warpo/frontend/CompilerImpl.cpp)：显式传入隐藏参数 `--frontend-gc-metrics` 时，读取插桩前端导出的计数器；普通编译不读取。

先按旧、新策略生成完整前端，再使用编译器同时输出的最终 WAT，经已有 WABT 加入名称后读取并插桩。之后不再运行通用优化 pass。插桩辅助函数不分配 GC 对象，不占用 shadow-stack 根槽，计数器使用 Wasm globals，不侵占线性内存。

计数范围覆盖前端初始化、解析和编译，定义如下：

- **根栈峰值**：初始 SP 减去执行期间最小 SP；观察每次根栈全局指针赋值。
- **帧清零字节数**：目标完全位于当前活动根栈区域的零值 `memory.fill` 长度之和。
- **标量零写字节数**：同一区域内，实际写入位模式全零的标量 store 宽度之和；处理整数窄化和浮点位模式。它包含 null 根写入，单独列出。
- **根扫描字节数**：GC runtime 中落在活动根栈区域的 load 宽度之和。非 GC 函数的根区域读取另行统计，四个负载均为零。
- **非空根扫描次数**：上述扫描读取到当前 SP 时加一。
- **线性内存页数**：前端编译结束时的 `memory.size`；内存不会缩小，所以也反映本次运行分配过的最大页数。

这些是 Wasm 执行语义中的字节计数，**不是 DRAM 总线流量、缓存 miss 或 CPU 周期数**。GC 的扫描指标只覆盖 shadow stack，不包括全局根、pin 列表和堆对象图。

每个负载都检查：插桩与未插桩输出相同、旧与新输出相同、结束时根栈恢复。两次完整实验的所有这些动态数值完全复现。

精确校准用例的期望值为：峰值 12 B、fill 清零 12 B、标量零写 25 B、根扫描 12 B、非空扫描 1 次。另检查堆上的清零不被算入根栈，以及有副作用的地址操作数只求值一次。

### 10.2 负载

1. **self**：待测前端编译完整前端工程的 `fast` target，与前文自举负载一致。
2. **nested16 / nested64 / nested128**：让待测前端解析和编译 16、64、128 层泛型嵌套。

嵌套输入的结构为：

```typescript
class Box<T> {
  value: T;
  constructor(value: T) { this.value = value; }
}
type L0 = i32;
type L1 = Box<L0>;
// ... 依次生成，直到 L128
export function keep(value: L128): L128 { return value; }
```

后者测量的是**编译器真实的递归类型解析调用**产生的根栈，不是模拟根帧，也不是把深度乘以静态帧大小得到估算值。它是受控压力负载，不代表车端业务代码的典型分布；没有执行生成的 `keep` 函数。

### 10.3 价值一：实际根栈峰值确实降低

| 负载 | 旧峰值 | 新峰值 | 减少 |
| --- | ---: | ---: | ---: |
| self | 13,732 B | 12,508 B | **8.91%** |
| nested16 | 4,712 B | 4,280 B | 9.17% |
| nested64 | 16,588 B | 11,720 B | 29.35% |
| nested128 | 32,716 B | 22,984 B | **29.75%** |

因此，“根帧缩小可能降低真实根栈峰值”在这些输入上已经得到直接验证。它仍不是任意输入的静态上界，也不是原生机器栈峰值或整个进程 RSS。

### 10.4 价值二：清零和根扫描确实减少

| 负载 | 帧 fill 清零：旧 → 新 | 减少 | 根扫描：旧 → 新 | 减少 | 旧 / 新扫描次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| self | 100,929,380 → 90,820,476 B | **10.02%** | 7,156 → 6,556 B | **8.38%** | 4 / 4 |
| nested16 | 16,727,464 → 15,874,628 B | 5.10% | 132 → 108 B | 18.18% | 1 / 1 |
| nested64 | 17,036,248 → 16,150,196 B | 5.20% | 5,224 → 3,784 B | 27.57% | 2 / 2 |
| nested128 | 17,548,984 → 16,618,644 B | 5.30% | 42,056 → 29,752 B | 29.26% | 5 / 5 |

在 self 中，另外有 3,957,004 B 的根区标量零写，旧、新相同。将它计入后，总零写为：

```text
旧：104,886,384 B
新： 94,777,480 B
减少：10,108,904 B，即 9.64%
```

这里统计重复执行的写入量，不是占用了一百多 MB 根栈。实际峰值仍只有十几 KB。
根扫描的绝对节约也只有 **600 B / 本次完整任务**，不能把 8.38% 推广成整个 GC 耗时改善 8.38%。

### 10.5 价值三：仍没有稳定运行加速证据

最终版本使用**原始、未插桩**的两个前端，在同一绑定后端上执行 self。每组预热 6 次，正式测量 40 对，按 AB / BA 交替。

| 指标 | 旧中位数 | 新中位数 | 中位数耗时变化 |
| --- | ---: | ---: | ---: |
| 完整进程 | 881.857 ms | 882.717 ms | +0.10% |
| 前端编译阶段 | 470.567 ms | 470.794 ms | +0.05% |
| 前端整体 `CompilationHIR` | 720.483 ms | 720.851 ms | +0.05% |

进一步按每两个 AB / BA 配对组成一个平衡块，对配对 log 耗时比做 20,000 次 block bootstrap。正值表示减少耗时：

| 指标 | 配对几何平均改善 | 经验 95% 区间 |
| --- | ---: | ---: |
| 完整进程 | +0.30% | **[-0.22%, +1.00%]** |
| 前端编译阶段 | +0.03% | **[-0.53%, +0.56%]** |
| 前端整体 | +0.23% | **[-0.35%, +0.95%]** |

区间均跨零，因此不能认定取得加速。中位数之比与配对几何平均不是同一个估计量，方向略有不同不矛盾。
前一组 40 对实验的编译阶段区间也跨零，为 [-1.61%, +0.85%]；其原始数据保留，没有只选择正向实验。

这些是共享开发主机上的经验区间，不是对量产硬件的性能保证，也不是证明真实效果精确等于零。
较少的根写入/扫描没有自动转化为可检出的完整任务加速，不能用前文最有利的一轮 4.27% 替代本节结果。

### 10.6 价值四：能降低根栈预算，但没有降低总线性内存

#### A. 真正重编译较小根栈配置，而不只是计算峰值

根据四个负载中最大的实测峰值向上取整到 16 B，重新编译前端：

| 策略 | `--stackSize` | 四个负载均通过，输出一致 |
| --- | ---: | --- |
| 旧 | 32,720 B | 是 |
| 新 | 22,992 B | 是 |

新预算少 **9,728 B（9.5 KiB），29.73%**。

额外进行了相同输入、相同预算的反例对照：

- `nested128`，新着色，`--stackSize 22992`：成功，输出与大预算旧前端完全一致。
- **同一输入**，旧着色，`--stackSize 22992`：失败。
- 失败栈首帧解析为 `~lib/rt/__decrease_sp`，后续为 `Resolver#resolveType`、`Resolver#resolveTypeArguments` 等，确认触发根栈保护检查，而不是用任意编译错误冒充容量改善。

因此，“在相同较小根栈预算下，新方案能完成旧方案无法完成的递归输入”有了直接工程证据。

**这些小预算仅为实验配置，没有生产安全余量；未修改正式的 262,144 B 配置。** 四个输入的峰值不是所有业务输入的上界，也没有证明这两个预算是各自的全局最小值。

#### B. 完整线性内存：未观察到改善

默认初始线性内存为 768 页（48 MiB），实际运行结果为：

| 负载 | 旧最终页数 | 新最终页数 | 减少 |
| --- | ---: | ---: | ---: |
| self | 3,072（192 MiB） | 3,072（192 MiB） | **0%** |
| nested16 | 768（48 MiB） | 768（48 MiB） | 0% |
| nested64 | 768（48 MiB） | 768（48 MiB） | 0% |
| nested128 | 3,072（192 MiB） | 3,072（192 MiB） | 0% |

还对未插桩 self 前端仅修改 Wasm memory section，将 initial 和 maximum 同时限制为同一页数，代码、数据、根栈配置保持不变，搜索固定内存成功边界：

| 策略 | 通过配置 | 相邻失败配置 |
| --- | ---: | ---: |
| 旧 | 2,302 页 | 2,301 页 |
| 新 | 2,302 页 | 2,301 页 |

2,302 页为 **150,863,872 B，143.875 MiB**。失败位于 `~lib/rt/itcms/__new` 分配路径，不是根栈保护函数；成功时均校验输出哈希。

搜索采用成功性单调的二分假设，并复核相邻边界及最多三个更低点；原始数据保留全部试验页数和失败栈。它不是遍历所有可能配置的全域最小值证明，且没有联合搜索根栈大小与堆容量。

**结论：根栈组件的容量配置收益已证明；整份线性内存的成功边界相同，不能声称产品总 RAM 已节省 29.73%。** 这里也未测量整个原生进程的 RSS。
